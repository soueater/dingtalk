## 新增需求：提示词增强功能（F-PE-01）

**需求**：将用户口语化输入自动优化为结构化、规范、无歧义的提示词。需明确触发方式、输入输出对应关系、优化规则、结果展示与使用、通用性与一致性。

**已交付**：`docs/功能设计-提示词增强.md`（v1.0，待确认）

**核心设计决策**：
- **触发**：默认手动按钮（不静默自动改写，尊重用户控制权）+ 智能建议轻提示（本地启发式判定，≥2条命中才提示）+ 快捷键。理由：自动改写用户输入有「好心改需求」的风险。
- **输入分级 L0-L3**：极简型/口语型/半结构型/已结构化。L3 不做增强，仅提示已是增强格式 → 这是**幂等性**的机制保障（防止反复增强导致提示词膨胀）。
- **输出**：固定 8 区块 Markdown 模板（产品目标/目标平台/页面结构/核心功能/视觉风格/关键组件/约束偏好/待确认）。选 Markdown 理由：人可读可编辑，LLM 可直接消费。
- **规则四层**：保留类(R-1~R-4 红线) → 补全类(R-5~R-8) → 规范化类(R-9~R-12) → 消歧类(R-13~R-15)。冲突时高层胜出。
- **推断标注**：所有非用户明示内容必须标 `[推断]` 前缀；冲突标 `[冲突]` 且两者都保留交由用户裁决，绝不自行取舍。
- **展示**：对比视图（原文 vs 增强结果并排），可编辑/复制/重生成/还原/使用。
- **技术保险**：输出后置「意图保全校验」——从原文抽取关键实体，回溯校验是否都出现在增强结果中，未通过则针对性重试。这是 R-1 红线的最后防线。
- **通用性来源**：增强规则领域无关（不绑行业），行业知识通过**可扩展术语映射表**注入。新增行业只需加条目，不改逻辑。
- **降级原则**：增强失败永远退回原文，绝不退回「半成品增强结果」。

**新增决策点 D5-D8**：默认触发方式(手动) / 默认强度(标准档) / 是否支持「使用并生成」(支持) / 术语映射表维护方式(内置常见行业+预留自定义)。

**已同步到工作计划**：架构图加入增强器（标记为旁路模块）、S1-2 增加提示词引导对标、S2-5 增加增强器专项设计、S3-3B 作为首个子模块实现、S4 增加专项测试项。

**Stitch 关键事实（多来源交叉验证）**：
- 2025.05 I/O 发布（前身 Galileo AI，Google 收购后更名）→ 2025.12 接入 Gemini 3 + Prototypes（多屏串联+转场）→ 2026.03 重构为 AI-native 无限画布 + Voice Canvas + Vibe Design + Direct Edits
- 界面演进：V1 左右分栏（左对话右画布）→ V2 三段式（提示词/画布/Agent日志）→ V3 无限画布
- 配额：Standard 350次/月（Gemini 2.5 Flash）、Experimental 50次/月（2.5 Pro，支持图片上传但无Figma导出）
- 生成耗时：Standard 理解~10s + 生成~40s；Experimental 60-90s
- 设备类型：MOBILE/DESKTOP/TABLET/AGNOSTIC；官方SDK支持 variants(variantCount 1-5, aspects: LAYOUT/COLOR_SCHEME/IMAGES/TEXT_FONT/TEXT_CONTENT)
- 仅英文界面，需18岁+，覆盖212国家

**Stitch 三大痛点（= 本项目差异化点）**：
- P-1 交互是「视觉态」非真实逻辑（点击不触发状态变化，给的是点击前/后两张图）
- P-2 编辑能力有限，本质只读预览（能复制hex但不能点进去调）
- P-3 跨屏设计一致性弱（第一页电光蓝第二页变靛蓝，需提示词显式约束）

**功能取舍矩阵结论（S1-5 §3）**：1:1复刻15项(45%) / 强化超越8项(24%) / 新增补齐6项(18%) / 适配改造1项 / 不实现13项。

**三大差异化点（立身之本）**：
1. 完整实时可视化编辑（对话+拖拽+属性面板三通道，Stitch 只有对话）
2. 真实可交互原型（基于Schema的真实交互逻辑，Stitch 是视觉态切换）
3. 设计Token驱动的强制一致性（解决P-3）

**可复用性（S1-6）**：R-A直接复用9项(21%) / R-B路径替换20项(47%) / R-C重新设计7项(16%) / R-D不可复用7项(16%)。结论：**可对标产品能力与交互体验，但不能照搬技术实现**——68%可复用，主体工作量在把云端路径替换为本地实现。

**三个关键成功因素**：CSF-1 Design JSON Schema质量 / CSF-2 Prompt工程抹平模型差异 / CSF-3 编辑器性能。

**对标基线确认**：形态对标2026.03理念，但布局用V2三段式（非无限画布），交互主线为「对话快路径 + 面板精确路径」双通道并存。

## T4 完成：S3-3A 工程骨架 + 配置面板

**交付**：`app/` 完整可运行工程 + `docs/S3-3A-进展说明.md`

**实测通过的版本栈**：Electron 44.4.5 / Vite 7.3.6 / React 19.3.0 / TypeScript 5.9.3 / Zustand 5 / electron-builder 26.15.3。**未使用 electron-vite**，改用自研 esbuild 脚本打包主进程与 preload，保持完全控制。

**工程结构**：
- `electron/main/` 8 个模块：index(窗口/安全策略) / secure-store(密钥加密) / config-store / llm-proxy(4适配器+SSE流式) / project-fs / export-fs / png-render(隐藏窗口光栅化) / ipc(统一 IpcResult 信封)
- `electron/preload/` contextBridge 暴露 `window.dsa.{project,config,llm,exporter,app}`
- `shared/design.ts` 全项目类型契约
- `src/` 渲染层：三段式布局 + 四类面板 + 画布 + 配置面板 + 预览/导出浮层

**核心架构要点（务必保留）**：
- **渲染函数三处共用**：`services/render/node.ts` 同时服务画布渲染、原型预览、导出 HTML → 所见即所得是结构性保证
- **画布用字符串 HTML + dangerouslySetInnerHTML**，非 React 组件树（性能与控制力）
- **PNG 导出用 Electron 隐藏窗口自己光栅化**，不引第三方渲染库
- **尺寸三态** `number | 'fill' | 'fit' | '50%'`，Token 引用 `$color.primary`
- **commit(label, mutator, {coalesceKey})** 事务化变更 + 反向历史栈；拖拽高频更新绕过历史栈，结束时合并一条

**踩过的坑（重要）**：
1. `npm install` 并发运行会导致 `EBUSY`（争抢同一 node.exe）→ 必须串行
2. electron postinstall 不自动下载二进制 → 用 `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ node node_modules/electron/install.js` 手动补
3. `@rollup/rollup-win32-x64-msvc` 原生包会损坏（表现为 42KB，正常 2.6MB）→ `npm install <pkg> --no-save --force` 修复
4. **不能用 `!app.isPackaged` 判断开发模式**：直接运行 dist 产物时它也为 true，会错误连接 Vite。必须由 dev 脚本显式注入 `NODE_ENV=development` + `DEV_SERVER_URL`
5. 当前 shell 环境自带 `ELECTRON_RUN_AS_NODE=1`，会导致 Electron 以纯 Node 模式启动而报错 → 启动前必须 `env -u ELECTRON_RUN_AS_NODE`
6. 沙箱/远程环境 GPU 进程可能反复崩溃 → 主进程已加 `DISABLE_GPU=1` 或 `--disable-gpu` 兜底开关

**验证结果**：tsc 零错误 / 主进程 esbuild 42KB / 渲染层 354KB(js)+29.5KB(css) / 端到端启动 5 进程稳定、日志零错误。
