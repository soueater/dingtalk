## 0. 评审速览（TL;DR）

本轮提出四项能力，**其中三项不是"从零造"，而是"接线 + 补渲染 + 补 AI 环节"** —— 项目里已有对应的类型定义或函数实现，只是尚未形成闭环。第四项是真实缺陷修复。

| 编号 | 功能 | 一句话目标 | 优先级 | 现有可复用底座 | 主要缺口 |
|---|---|---|---|---|---|
| **F-ST-03** | 修复「生成设计变体」报错 | 让变体生成稳定可用 | **P0** | 全链路已实现 | **输出预算 / 校验重试 / jsonMode 兼容** 三处缺陷 |
| **F-ST-01** | 设计规范引用能力 | 生成结果锁定到指定规范 | **P1** | `STYLE_PRESETS`（4 套完整 Token）+ `getPreset()` | 规范实体持久化 / 绑定 / 切换 / 校验 四环节 |
| **F-ST-04** | 页面 AI 优化能力 | 对已生成页面做 AI 改写 | **P1** | `buildEditPrompt()` + `TEMP.edit` + `commit` 事务 | **该函数零调用方**（死代码）+ 无整页入口 + 无 diff 预览 |
| **F-ST-02** | 页面自动补全能力 | 自动补页 + 自动补动效交互 | **P2** | `Node.states` 类型、`Flow.trigger/transition` 类型 | 渲染层完全未消费 `states`；无自动生成 states/flows 的 AI 环节 |

**落地顺序一句话**：先修变体（打底，把"校验+重试"范式沉淀为公共能力）→ 再建规范基准 → 再做页面优化（消费基准）→ 最后做自动补全（消费基准 + 补动效渲染）。

**需评审确认的决策点**见 §7。

## 2. 需求一 · 设计规范引用能力（F-ST-01）

### 2.1 目标

让「设计规范」成为一个**可建立、可绑定、可切换、可校验**的一等实体，使 AI 生成的任意页面都能锁定到指定的规范上，从而解决当前的核心痛点：

> **当前问题**：每次生成，阶段 B「Token 定稿」都由模型自由发挥（`buildTokensPrompt`），没有可复用的基线。同一项目内多页并排看时，主色、字族、圆角可能是"同一套"但边界情况漂移；换一个项目再生成，风格完全不可复现。

一句话：**把「模型每次现编一套 Token」变成「先声明规范，再按规范画」。**

### 2.2 适用场景

| 场景 | 说明 | 价值 |
|---|---|---|
| **品牌一致性**（核心场景） | 已有 VI / 设计系统，要求生成页面必须用指定主色、字族、圆角 | 达成 S1-2 §4.2 中「字体锁定正确、色板回归真实」的效果 |
| **多方案并行探索** | 同一份需求，分别用「清透蓝」「墨韵」画一版，横向对比 | 替代当前需要手工改 Token 的低效做法 |
| **老项目续作** | 已有项目文件，新增页面需沿用既有规范 | 避免新旧页面风格割裂 |
| **交付合规** | 团队规范要求页面不得使用某些颜色（如破坏性操作用强调色） | 通过**负面规则**约束生成 |

### 2.3 关键能力

#### 2.3.1 规范实体的建立（导入）

规范来源三条路径，**优先级从高到低**：

| 路径 | 说明 | 优先级 |
|---|---|---|
| **内置规范** | 直接取 `STYLE_PRESETS` 四套（清透蓝 / 墨韵 / 暖橙 / 青碧），零成本 | **P1**（首发必做） |
| **导入规范文件** | 支持粘贴 / 导入 JSON（`{name, tokens}`），对齐 Stitch 的 `design.md` 思路 | **P1** |
| **从项目派生** | 以当前项目 `design.tokens` 为模板存为新规范（"把这一版风格存下来"） | **P2** |

**建议数据结构**（新增，不改动现有 `Tokens` 契约）：

```ts
// shared/design.ts 新增
export interface DesignSpec {
  id: string
  name: string
  desc?: string
  source: 'builtin' | 'imported' | 'derived'
  tokens: Tokens
  rules?: SpecRules
  createdAt: string
}

/** 对齐 Stitch design.md 的「不要做什么」负面规则 —— S1-2 §4.2 明确其价值极高 */
export interface SpecRules {
  dos?: string[]
  donts?: string[]
}
```

#### 2.3.2 规范绑定

**两级绑定**，就近优先：

| 层级 | 字段 | 语义 |
|---|---|---|
| 项目级（默认） | `DesignJSON.meta.specId?: string` | 全项目默认规范 |
| 页面级（覆盖） | `Page.specId?: string` | 该页单独指定，用于「同一项目内多规范并存」 |

> **用户需求原话对应**：「在绘制不同页面时可选择、引用不同规范」→ 这正是 `Page.specId` 覆盖 `meta.specId` 的两级设计。

#### 2.3.3 规范切换（重解析）

规范切换**不是简单替换 `tokens` 对象**，而是一次「重解析」：

```
切换规范 → tokens 整体替换 → 触发渲染层全量重解析
```

- 现有渲染链路天然支持：`buildTokenMap()` → `resolveValue()` / `resolveColor()`，因节点 `style` 中存的是 `$color.primary` 这类**引用**而非字面值（`parse.ts` 的 `REF = /^\$([a-zA-Z]+)\.([\w-]+)$/`），替换 `tokens` 后**所有引用点自动跟着变**。
- **关键约束**：必须承认「规范切换会覆盖手改的颜色」。设计上要求：
  1. 切换前明确提示「将覆盖 N 处非 Token 引用色值」；
  2. 走 `commit('切换设计规范：X', ...)` 单事务，可一键撤销；
  3. 使用 `coalesceKey: 'switch-spec'` 避免连续切换刷爆撤销栈。

#### 2.3.4 一致性校验（这个能力是 F-ST-01 的差异化价值）

**规范漂移检测（Spec Drift Check）** —— 扫描页面树，找出违反绑定规范的地方：

| 检查项 | 判定 | 修复动作 |
|---|---|---|
| 未使用 Token 引用 | `style.fill` 是字面色值而非 `$color.*` | 「转为 Token 引用」（可自动匹配最近色） |
| 使用了不存在的 Token | 引用 `$color.xxx` 但规范里没定义 | 高亮 + 建议替换项 |
| 违反负面规则 | 文案含「不要用全大写标题」但仍 `textTransform: uppercase` | 提示 + 一键修正 |
| 色值不在规范色板内 | 字面色值 `#FF0000` 不在规范 `color` 集合中 | 提示为「规范外颜色」 |

产出形态：右下角**「规范校验」面板**（复用 `RightPanel` 的 Tab 机制，见 `components/layout/RightPanel.tsx:8` 现有 `'props' | 'flows'` 范式，扩展为 `'props' | 'flows' | 'spec'`）。

#### 2.3.5 规范导出

把当前生效规范导出为 JSON / Markdown（对齐 Stitch 的 design.md 格式），供**跨项目、跨工具复用**（S1-2 §4.2 的「跨工具一致性的共享事实源」洞察）。

### 2.4 与现有流程的协同

**核心改动点在生成流水线的「阶段 B」**：

```
当前：阶段A 规划 → 阶段B 「模型自由定稿 Token」 → 阶段C 逐页生成
                          ↑ 无基线，每次重编

改后：阶段A 规划 → 阶段B 「按绑定规范定稿 Token」 → 阶段C 逐页生成
                          ↑ 有基线，可跳过模型调用
```

**两种协同模式**：

| 模式 | 触发 | 行为 |
|---|---|---|
| **规范直用（默认，推荐）** | 项目已绑定规范 | **跳过阶段 B 的模型调用**，直接把规范 `tokens` 注入阶段 C。省一次请求、风格 100% 可控 |
| **规范微调** | 用户在生成面板主动勾选「允许 AI 在规范基础上微调」 | 仍调模型，但 Prompt 改为「以下规范是基线，只允许调整 X」 |

阶段 C 的 `buildPagePrompt` 需增加规范段落：把 `SpecRules.donts` 作为显式负面约束注入，降低劣质生成。

### 2.5 优先级与依赖

- **优先级：P1**（核心交付物）。理由：它是 F-ST-02 与 F-ST-04 的**校验基准** —— 「自动补全补到什么标准」「优化是否对齐规范」都需要一个规范实体存在。
- **依赖**：无强前置（可直接基于 `STYLE_PRESETS` 起步）。
- **被依赖**：F-ST-02、F-ST-04。

### 2.6 完成标准（DoD）

- [ ] 可在 UI 中选择 / 导入 / 新建规范，并持久化到项目文件
- [ ] 支持项目级 + 页面级两级绑定，页面级可覆盖
- [ ] 切换规范后画布、预览、导出三处同步重解析，无残留旧色值
- [ ] 切换操作走单事务，可一键撤销
- [ ] 规范校验面板可列出至少 4 类漂移项，并支持一键修正「转为 Token 引用」
- [ ] 规范可导出为 JSON，导出文件可再次导入且往返无损
- [ ] 项目文件向后兼容：旧文件（无 `specId`）打开不报错，按「未绑定」处理

## 3. 需求二 · 页面自动补全能力（F-ST-02）

### 3.1 目标

两个层面的「补全」，**建议拆为两个独立子能力**：

| 子能力 | 目标 | 现状 |
|---|---|---|
| **2A · 页面补全** | 自动推断并补齐缺失页面（访问链路完整性） | 无（`generate.ts` 只按 `plan.pages` 逐页生成） |
| **2B · 动效与交互补全** | 为已有页面自动补 `states`（悬停/按下/聚焦）与 `flows`（跳转） | 类型已定义，**渲染层零实现** |

一句话：**把「画完之后还要手工补空页面、手工连跳转、手工写悬停态」变成一次自动完成。**

### 3.2 适用场景

| 场景 | 说明 |
|---|---|
| 生成后链路断裂 | 模型只生成了「首页 / 列表页」，缺少「详情页 / 结算页」，点进去是死路 |
| 交互缺失 | 生成的按钮、卡片、列表项**没有任何视觉反馈**，原型演示时"点了没反应" |
| 跳转缺失 | `flows` 为空，预览模式点不动（`PreviewModal.tsx:55` 的 `goMap` 为空对象） |
| 表单缺省市 | 表单元素无聚焦态、错误态，看起来不像真表单 |

### 3.3 关键能力

#### 3.3.1 页面补全（2A）

**输入**：当前项目全部页面清单 + 各页职责 + 绑定规范。
**输出**：建议新增的页面列表（含 `id / name / purpose / keySections`）。

**关键设计 —— 两段式，不做静默插入**：

```
1. 分析 → 产出「补全建议清单」（不落盘）
2. 用户勾选 → 逐页调已有阶段 C 生成 → 逐页 commit
```

理由（与 `docs/功能设计-提示词增强.md` §2.1 的「显式触发，不做静默改写」原则一致）：自动新增页面会改变项目结构，**静默插入会让用户困惑且难以撤销**。

**断链检测算法**（可复用现有数据）：
- 遍历 `design.flows`，收集所有 `to` 指向的 `pageId`；
- 找出「被引用但不存在」的页 → 断链；
- 找出「以某个 CTA 文案命名但无对应页面」的节点（如按钮文案「去支付」但无支付页）→ 建议补页。

#### 3.3.2 动效与交互补全（2B）—— 这是工程量主体

**消费已定义但未渲染的 `Node.states`**：

```
Node.states = {
  hover?:  { style?, props? },
  active?: { style?, props? },
  focus?:  { style?, props? },
}
```

**渲染层需要补的实现**（`services/render/node.ts`）：

| 项 | 现状 | 需补 |
|---|---|---|
| `styleToCss` | 只处理静态 `style` | 输出 `states` 为**作用域 CSS 类**（`.n-{id}:hover { ... }`），而非内联样式 |
| 内联样式限制 | 内联样式**无法表达伪类** | 必须为带 `states` 的节点生成 `<style>` 规则块，与内联样式合并 |
| Token 解析 | `resolveValue` 已支持 | 直接复用，`states.style` 中的 `$color.*` 同样走解析 |
| 预览模式 | `translateX` 动画已实现（`PreviewModal` 的转场） | 需补 `:hover` / `:active` 在预览态同样生效 |

**AI 自动填充 states 的策略**（按元素类型推导，无需模型即可覆盖 80%）：

| 元素类型 | 自动补的 states |
|---|---|
| `button` | hover（提亮/加深 `primaryHover`）、active（`primaryActive`）、focus（外发光） |
| `card` / `listItem` | hover（阴影升一档 `shadow.md`）、cursor: pointer |
| `input` / `textarea` / `select` | focus（边框转 `primary` + 光晕） |
| `switch` / `checkbox` / `radio` | active（缩放 0.96） |
| `tag` / `chip` | hover（背景加深一档） |

> **工程判断**：以上映射是**规则化**的，用本地启发式即可完成（对齐 `enhancer.ts` 的 `enhanceHeuristic` 思路）—— 零延迟、零成本、100% 确定。仅当用户要求「更有创意/更丰富的动效」时才调模型。**这是本能力能落地为 P2 而非 P0 的关键**：先做本地规则版，AI 版为增强。

#### 3.3.3 交互补全（flows）

复用 `Flow.trigger` 与 `Flow.transition`，自动推理：

| 推理规则 | 产出 flow |
|---|---|
| 按钮/列表项文案与某页面名语义匹配（「去结算」→「结算页」） | `flow { from, fromPage, to, trigger: 'click' }` |
| 存在 `back` 语义节点（返回箭头） | `trigger: 'back'` |
| 页面存在层级关系（列表→详情） | 自动选 `transition: 'slide-left'` |

产出后**仍需用户确认**（同 §3.3.1 的原则），并可复用 `normalizeFlows()`（`generate.ts:239`）做合法性过滤（过滤指向不存在页面的跳转、截断至 40 条）。

### 3.4 与现有流程的协同

```
生成流水线（不变）
  ↓
[新增] 补全阶段（生成完成后可选触发）
  ├─ 2A 断链检测 → 建议补页清单 → 用户勾选 → 复用阶段C逐页生成
  └─ 2B 规则化补 states/flows → 预览对比 → 用户勾选 → commit
```

- **2A 复用阶段 C 的 `buildPagePrompt` + `askJson`**，零新增 Prompt 开发。
- **2B 大部分是纯本地规则**，不依赖模型。
- 两者都走 `commit()` 单事务 + `coalesceKey`，可撤销。

### 3.5 优先级与依赖

- **优先级：P2**（体验增强）。理由：
  1. **强依赖 F-ST-01** —— 「补到什么标准」需要规范基准；
  2. **需要渲染层新增伪类/状态渲染**，是全轮唯一涉及渲染内核改动的能力，风险与工作量最高；
  3. 可以拆成两批：先 2B 的**本地规则版**（不依赖规范，可提前），再 2A 的 AI 补页。
- **依赖**：F-ST-01（2A 强依赖，2B 弱依赖）；渲染层状态支持。
- **风险**：`states` 渲染需改动 `renderNode` 的 CSS 生成路径，**会影响画布、预览、导出、变体缩略图四处**（这四处共用同一渲染实现），必须回归测试。

## 4. 需求三 · 修复「生成设计变体」报错（F-ST-03）

> 本节按 `docs/测试报告.md` §4 既有体例（现象 / 根因 / 修复）成文。

### 4.1 现象

点击画布工具栏「变体」按钮（`CanvasToolbar.tsx:78` → `openOverlay('variants')` → `VariantModal`），选择维度与数量后点「生成变体」：

| 现象 | 出现条件 |
|---|---|
| Toast 报错「变体生成失败：模型未返回任何变体」 | 高频 |
| Toast 报错「变体生成失败：模型未返回可解析的 JSON」 | 中频 |
| Toast 报错「变体生成失败：HTTP 400 …」（映射为 `E_UNKNOWN`） | 视服务商 |
| 只生成出 1 个变体（选了 3 个） | 低频但稳定复现 |

**关键区分**：这不是「偶发网络问题」，而是**架构层面的必然结果** —— 见根因 1。

### 4.2 根因分析

按**确定性从高到低**排序。前 3 条为静态代码可直接证明的确定性结论，后 2 条为次要因素。

---

#### 根因 1（高置信 · 主因）：单次请求产出多个完整页面树，必然超出输出预算

**证据链**：

| # | 事实 | 位置 |
|---|---|---|
| 1 | Prompt 要求**一次请求返回 N 个完整页面树**：`"variants": [{ aspects, rationale, root }]`，其中 `root` 是完整 `NODE` | `variants.ts:71-82`（输出格式定义） |
| 2 | 且明确要求「每个变体都必须是一个**完整可用**的页面」 | `variants.ts:66`（关键约束） |
| 3 | `maxTokens` **硬编码 12000** | `variants.ts:110` |
| 4 | UI 允许一次生成 **3~4 个**（`VariantModal.tsx:152` 的 `[2,3,4]`；服务端上限 `Math.min(5, count)`） | `variants.ts:100` |

**体量估算**：一个移动端设计页约 30-60 个节点，节点 JSON 含 `id/type/name/layout/style/props/children`，缩进后单节点约 0.4-0.8 KB，含中文文案更高。一页约 15-30 KB ≈ **5-10K tokens**。3 个变体 ≈ **15-30K tokens**，**远超 12000 上限**。

**后果**：模型输出被服务端截断 → `lenientParse` 的 `closeBrackets()`（`parse.ts:85`）只能补出「语法合法但语义残缺」的 JSON → `parsed.variants` 为空或只含第 1 个元素 → 抛「模型未返回任何变体」或只返回部分变体。

> **这是"必然"，不是"偶发"** —— 只要页面稍复杂、变体数 ≥ 3，几乎必然命中。

---

#### 根因 2（高置信 · 放大因素）：`maxTokens: 12000` 硬编码，同时绕过两层约束

**证据**：

```ts
// variants.ts:110 —— 硬编码，未读取任何配置
{ temperature: 0.85, maxTokens: 12000, jsonMode: true }
```

| 冲突面 | 实际值 | 说明 |
|---|---|---|
| 用户配置的默认 `maxTokens` | **8192** | `config.store.ts:88` |
| 生成流水线阶段 A/B/C | 4096 / 3072 / **8192** | `generate.ts:111, 135, 177` |
| 变体链路 | **12000** | 覆盖了用户配置 |

**双重问题**：
1. **不尊重用户配置** —— 用户在配置面板把 `maxTokens` 调小（例如受额度限制的模型），变体链路照样请求 12000；
2. **12000 本身可能超出模型/服务单次输出上限** —— 部分 OpenAI 兼容服务对 `max_tokens` 有硬上限，超出直接返回 **400**；`mapHttpError` 未识别 400 → 落到 `E_UNKNOWN`（`llm-proxy.ts`），用户看到的是一个无法定位的原始错误。

---

#### 根因 3（高置信 · 结构性缺陷）：变体链路**完全没有**「校验 + 修复重试」保护

**对比证据** —— 项目里唯一健壮的 JSON 获取范式是 `askJson`，它做了 5 件事：

```ts
// generate.ts:47-80
for (let attempt = 0; attempt < 2; attempt++) {
  const messages = attempt === 0 ? [...] : [
    ...,
    { role: 'assistant', content: lastRaw.slice(0, 4000) },   // 回灌上次输出
    { role: 'user', content: buildRepairPrompt(lastRaw, lastErr) },  // 要求修复
  ]
  const res = await chatOnce(...)
  const jsonText = extractJson(lastRaw)
  if (!jsonText) { lastErr = '未能从输出中提取出 JSON 对象'; continue }
  const parsed = lenientParse(jsonText)
  const v = validate(...)          // ← 结构校验
  if (v.ok) return parsed
  lastErr = v.errors.join('；')     // ← 带错误原因重试
}
```

**而变体链路只做了 3 步，缺了后 2 步**：

```ts
// variants.ts:115-119 —— 无校验、无重试
const jsonText = extractJson(res.content)
if (!jsonText) throw new Error('模型未返回可解析的 JSON')   // ← 直接抛，不重试
const parsed = lenientParse(jsonText) as {...}
if (!parsed?.variants?.length) throw new Error('模型未返回任何变体')  // ← 直接抛，不重试
```

**结论**：生成流水线对模型输出波动有韧性，变体链路**零韧性**。同样一次截断，生成链路会修复重试，变体链路直接报错。

---

#### 根因 4（中置信 · 兼容性）：`jsonMode: true` 无条件启用，部分服务商不支持

**证据**：

```ts
// llm-proxy.ts:93（openai）与 :221（openai 兼容）
...(o.jsonMode ? { response_format: { type: 'json_object' } } : {}),
```

该字段**无条件附加**，没有「服务商是否支持」的能力开关。部分 OpenAI 兼容服务（DeepSeek 早期版本、若干聚合网关、自建 vLLM 的部分版本）不支持 `response_format` → 返回 **400** → 映射为 `E_UNKNOWN`。

另注 Anthropic 分支（`llm-proxy.ts:119, 140`）用「预填充 `{` 诱导」方案：

```ts
const msgs = o.jsonMode ? [...rest, { role: 'assistant', content: '{' }] : rest
// 事后
if (o.jsonMode && content && !content.trimStart().startsWith('{')) content = '{' + content
```

当模型返回空内容时 `content` 为空串（`content &&` 短路），后续 `extractJson` 必然返回 `null` → 报「模型未返回可解析的 JSON」。

---

#### 根因 5（低置信 · 代码卫生）：两处死代码造成误导

**(a) 「恢复 Token」是假动作**：

```ts
// variants.ts:148-151
// 恢复 Token（变体不应污染全局 Token，除非用户采纳）
if (JSON.stringify(useProjectStore.getState().design.tokens) !== originalTokens) {
  ui.toast('info', '变体未修改全局设计 Token，采纳后才会生效')
}
```

注释写「恢复」，代码只做了一次**比较 + toast**，没有任何恢复动作。且 `generateVariants` 全程**从未写入 `store.tokens`**，该条件**恒为假**，是彻底的空转代码 —— 会误导后续维护者以为 Token 保护已实现。

**(b) `generateNodeVariants` 零调用方**：`variants.ts:165` 的局部元素变体生成已完整实现（含 `replaceInTree` 辅助函数），但全项目 grep 确认**无任何调用方**，属死代码。

---

#### 附带发现（非报错主因，但需一并修）

- **`VariantModal` 缩略图宽度边界**（`VariantModal.tsx:150` 附近）：


### 4.3 解决方案

## 5. 需求四 · 页面 AI 优化能力（F-ST-04）

### 5.1 目标

对**已生成**的页面做 AI 改写，两条入口：

| 入口 | 主导方 | 说明 |
|---|---|---|
| **自动优化** | AI 主导 | 用户不写提示词，AI 按「可读性 / 层次 / 一致性 / 规范符合度」自行诊断并改写 |
| **提示词驱动优化** | 用户主导 | 用户写自然语言指令（「把主按钮改到导航栏下方」「配色更克制一些」），AI 按指令改 |

一句话：**从「生成完就定型」变成「生成完还能持续打磨」。**

### 5.2 适用场景

| 场景 | 说明 |
|---|---|
| 生成结果"能用但不好看" | 层次不清、留白不当、字阶混乱 —— 无需重新生成，直接优化 |
| 局部不满意 | 「这个卡片太挤了」「标题不够突出」—— 用提示词精准指定 |
| 规范落地 | 生成时未绑定规范，事后想「把这个页面对齐到清透蓝规范」 |
| 多轮迭代 | 生成 → 优化 → 再优化，逐步逼近目标 |
| 跨页统一 | 同一套卡片样式在多页不一致，希望能统一 |

### 5.3 关键能力

#### 5.3.1 自动优化（AI 主导）

**诊断维度**（建议规则化 + 模型结合，对齐 `enhancer.ts` 的 L0~L3 分级思路）：

| 维度 | 规则化可检测项 | 需模型判断 |
|---|---|---|
| 视觉层次 | 字阶是否递增（`font.h1 > h2 > h3 > body`）、对比度是否达 WCAG AA | 层次是否服务于信息优先级 |
| 间距节奏 | 间距是否在 `space` Token 阶梯上、是否存在 > 64px 的孤岛间距 | 分组是否合理 |
| 一致性 | 同类元素（多个按钮）样式是否统一 | — |
| 规范符合度 | **复用 F-ST-01 的漂移检测** | — |
| 可读性 | 行高比、行长（移动端 35-50 字符） | 文案是否过长 |
| 冗余/缺失 | 空占位、重复区块、无意义的 `frame` 嵌套 | 是否缺少必要区块 |

**产出**：优化建议清单（含「问题 → 建议 → 影响元素 id」），用户勾选后应用。

#### 5.3.2 提示词驱动优化（用户主导）—— 复用已有死代码

**关键复用点**：项目里**已经有这个能力的完整 Prompt 模板**，只是从未接线：

```ts
// prompt-templates.ts:235 —— 零调用方
export function buildEditPrompt(design: unknown, instruction: string, selectedIds: string[]): string {
  return `你是 Design JSON 编辑助手。用户想修改当前设计。
  ...
  请输出一个 JSON 补丁（JSON Patch 风格，但用简化语义）：
  { "ops": [
      { "op": "update", "id": "节点id", "style": {...}, "layout": {...}, "props": {...} },
      { "op": "add", "parent": "父节点id", "index": 0, "node": NODE },
      { "op": "remove", "id": "节点id" },
      { "op": "replaceContent", "id": "节点id", "content": "新文本" }
  ], "explanation": "一句话说明你做了什么" }
  只输出 JSON。只做用户要求的最小修改，不要顺手改动其它内容。`
}
```

**已有零件清单**：

| 零件 | 状态 |
|---|---|
| `buildEditPrompt` Prompt 模板 | ✅ 已实现（**未接线**） |
| `TEMP.edit = 0.2`「精确改稿，避免误改其他内容」 | ✅ 已定义（未使用） |
| `TEMPERATURE_PRESETS.edit` 配置档 | ✅ 已定义 |
| `commit(label, mutator, {coalesceKey: 'edit-prompt'})` 事务 | ✅ 已实现且 `Inspector.tsx:641` 已有 `coalesceKey: 'edit-prompt'` 使用先例 |
| ops → 页面树的**应用器**（applyPatch） | ❌ **缺失** —— 这是主要开发量 |
| 整页级优化入口 UI | ❌ 缺失（现有 `AiPanel` 是「生成」面板，不是「改写」面板） |

**结论**：F-ST-04 ≈ 「接线已有 Prompt + 补一个 ops 应用器 + 补 UI」。**四项功能中单位成本最低、用户可感知价值最直接的一项。**

**ops 应用器设计要点**：

| op | 语义 | 注意 |
|---|---|---|
| `update` | 就地合并 `style` / `layout` / `props`（**浅合并非替换**） | 只改指定字段，保护用户手改 |
| `add` | 在 `parent` 的 `index` 插入节点 | `index` 越界需 clamp；新节点需 `repairNode` |
| `remove` | 删除节点 | 需级联清理引用它的 `flows` |
| `replaceContent` | 修改文本节点的 `props.content` | 最常用，风险最低 |

**意图保全约束**（复用 `enhancer.ts` 的 R-13 意图保全校验思路）：
- 优化不得删除原有**信息点**（除非用户明确要求）；
- 不得改变页面**语义类型**（按钮还是按钮）；
- 变更节点数超过阈值（如 > 50%）时，需二次确认「这看起来是大改，确定吗？」

#### 5.3.3 diff 预览与选择性采纳（关键差异化）

**必须先看到改了什么，再决定是否接受。** 这与 §4 P1-1 的「变体补丁」共用同一套 diff 渲染：

```
优化前 ──┐
         ├── 并排对比视图（复用 VariantModal 已有的 baseHtml 对比范式）
优化后 ──┘
         ↓
「采纳全部」/「逐条勾选采纳」/「放弃」
```

**局部接受**是核心价值 —— 用户可能只想要「间距调整」，不想要「文案改写」。ops 列表天然支持逐条勾选。

#### 5.3.4 可撤销

所有应用走 `commit('AI 优化：<explanation>', mutator)`，单事务入栈，`Ctrl+Z` 一键回退。连续优化用 `coalesceKey: 'ai-optimize'` 合并粗粒度历史。

```
                        ↑

      （读 F-ST-01 规范）  （用 buildEditPrompt）
```

### 6.3 优先级排序

沿用 `docs/任务分解-WBS.md` 的优先级范式：

| 优先级 | 定义 | 本轮归属 |
|---|---|---|
| **P0** | 阻塞性 —— 不完成后续无法开展 | **F-ST-03**（变体功能当前不可用，且是其余三项的范式来源） |
| **P1** | 核心交付物 —— 决定产品可用性 | **F-ST-01**、**F-ST-04** |
| **P2** | 体验增强 —— 核心链路跑通后补充 | **F-ST-02** |

**排序理由**：

1. **F-ST-03 必须最先** —— 变体功能是**已上线功能的真实缺陷**，用户一用就报错；且它的修复过程会产出 F-ST-04 所需的两个范式（ops 补丁、diff 预览）。不先做它，F-ST-04 要重复一遍同样的设计。
2. **F-ST-01 第二** —— 它是「基准」。没有基准，F-ST-02 不知道「补到什么标准」，F-ST-04 的自动优化也不知道「跟谁对齐」。
3. **F-ST-04 第三** —— 复用度最高（Prompt/温度/事务均已就绪，只缺应用器与 UI），投入产出比最佳。
4. **F-ST-02 最后** —— 工程量最大（唯一需要改渲染内核，且改动波及画布/预览/导出/变体缩略图四处），风险最高，且强依赖 F-ST-01 与 F-ST-03 的成果。
