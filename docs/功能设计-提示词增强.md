# 提示词增强功能设计（F-PE-01）

> 归属：望舒 · AI 生成能力
> 版本：v1.0 ｜ 状态：已定稿
> 关联文档：`S2-5-LLM接入与Prompt方案.md`

---

## 1. 功能定位

用户用自然语言描述想要的产品界面时，表达往往是**口语化、碎片化、隐含大量未言明前提**的。直接把这些原始描述交给模型，会导致：

- 生成结果不稳定，同一描述多次生成差异巨大
- 关键信息缺失（未说设备、未说风格），模型自行猜测且每次猜得不一样
- 跨页面风格不一致，因为描述中没有可复用的设计基线

**提示词增强（Prompt Enhancer）** 的职责：在不改变用户原始意图的前提下，把口语化需求**补全、规范化、结构化**，产出供生成引擎使用的标准需求描述。

一句话：**把「想要个记账的 App」变成一份可执行的设计需求简报。**

---

## 2. 触发方式

### 2.1 设计原则：显式触发，不做静默改写

| 方案 | 结论 | 理由 |
|---|---|---|
| 自动静默增强 | ✗ 不采用 | 用户看不到自己的话被改成了什么，生成结果不符预期时无法定位原因 |
| 手动显式触发 | ✓ 采用 | 用户掌控感强，可对比、可编辑、可拒绝 |
| 计数触发（如第 3 次生成自动启用） | ✗ 不采用 | 行为不可预测，用户困惑 |

### 2.2 具体触发入口

| 入口 | 操作 | 快捷键 | 说明 |
|---|---|---|---|
| 主入口 | 点击输入框下方「增强提示词」按钮 | `Ctrl/Cmd + K` | 对输入框当前内容做增强 |
| 二次入口 | 增强结果卡片内「重新生成」 | — | 对同一原始输入重新跑一次（模型有随机性，可能得到更好版本） |

### 2.3 前置条件与降级

- **未配置模型**：仍可触发。此时走**纯本地启发式增强**（见 §5.2），不调用模型，零延迟、零成本。
- **已配置模型**：优先走 LLM 增强；若调用失败（网络/额度/格式），**自动回退**到本地启发式，并在结果卡片标注「模型调用失败，已使用本地规则增强」。

## 3. 输入分级与建议策略

增强前先对输入分级，避免对已经足够好的输入做无用改写。

| 级别 | 判定条件 | 处理策略 |
|---|---|---|
| **L0** | 长度 ≤ 6 字 | 提示「描述太短」，仍执行增强但结果会大量标注 `[推断]` |
| **L1** | 长度 < 20 字，或缺少结构性词汇（页面/包含/列表…） | 强烈建议增强 |
| **L2** | 长度 < 80 字，或未指定风格/设备 | 建议增强 |
| **L3** | 长度 ≥ 80 字且已含结构、风格、设备信息 | 不主动建议，但用户仍可手动触发 |

判定为 L2/L3 时，**不自动触发**，仅在输入框旁以弱提示呈现「建议先增强提示词」。

---

## 4. 输入输出对应关系

### 4.1 输入

- 用户原始输入：任意自然语言，长度 1 ~ 5000 字
- 可选上下文：当前项目设备倾向（若用户从已有项目内发起）

### 4.2 输出：固定 8 区块 Markdown 模板

严格固定结构，保证跨场景一致性（无论输入是点餐 App 还是企业后台，输出都是同一套骨架）。

```markdown
## 1. 产品概述
一句话说明这是什么产品。

## 2. 目标用户与场景
谁会用它、在什么情况下用。

## 3. 页面结构
按顺序列出需要的页面，每行一个：`页面名` — 该页面的作用。

## 4. 各页面关键区块
每个页面下列出 3~6 个自上而下的区块。

## 5. 核心交互
用户的关键操作路径与页面跳转关系。

## 6. 视觉风格
色彩倾向、气质、圆角与间距偏好。

## 7. 设备与尺寸
手机端 / 平板 / 桌面端，以及理由。

## 8. 待确认事项
用户描述中不明确、需要进一步确认的点；若无则写"无"。
```

**为什么是这 8 个区块**：恰好覆盖生成流水线三个阶段（A 规划 / B Token / C 逐页）所需的全部输入信息，且与用户心智模型自然对应，不需要专业知识即可审阅。

## 5. 优化规则

### 5.1 四层规则体系

| 层 | 规则编号 | 内容 |
|---|---|---|
| **补全层** | R-1 ~ R-4 | 补全未言明的设备、风格、页面数量、核心路径 |
| **规范层** | R-5 ~ R-9 | 口语术语 → 设计术语；模糊量词具体化；统一命名 |
| **消歧层** | R-10 ~ R-12 | 检出内部矛盾并标注 `[冲突]`；歧义词给出选定解释 |
| **保守层** | R-13 ~ R-15 | 意图保全校验；不得新增用户未提的核心业务功能；不得删除用户明确要求 |

### 5.2 逐条规则明细

#### 补全层

| 编号 | 规则 | 示例 |
|---|---|---|
| R-1 | 未指定设备时，依据关键词推断并标注 `[推断]` | 「做个网页后台」→ `[推断] 桌面端 1440×900` |
| R-2 | 未指定视觉风格时，采用「清透蓝」中性方案并标注 `[推断]` | → `[推断] 清透蓝配色：主色 #3B82F6，圆角适中` |
| R-3 | 页面数量缺失时，依据功能点数量推断，控制在 2~6 个 | 「一个记账 App」→ 推断出首页/记账/报表/我的 |
| R-4 | 未说明跳转关系时，补出「列表 → 详情」的主路径 | — |

#### 规范层

| 编号 | 规则 | 示例 |
|---|---|---|
| R-5 | 主观形容词 → 可执行的设计约束 | 「好看点」→「视觉层级清晰、留白充足、配色协调」 |
| R-6 | 模糊量词具体化 | 「几个页面」→「3 个页面」 |
| R-7 | 口语词 → 设计术语 | 「顶上那条」→「顶部导航栏」 |
| R-8 | 页面命名统一化 | 「个人主页」/「我的」→ 统一为 `个人中心` |
| R-9 | 组件命名对齐组件库 | 「那种点一下的东西」→「按钮（button）」 |

#### 消歧层

| 编号 | 规则 | 示例 |
|---|---|---|
| R-10 | 检出矛盾并标注 `[冲突]`，不擅自取舍 | 「要简洁但信息要多」→ `[冲突] 简洁与信息密度高存在张力，建议分层展示` |
| R-11 | 多义表达选定最合理解释并注明 | 「卡片」→ 依据上下文判定为「内容卡片」而非「银行卡」 |
| R-12 | 未提及但强依赖的前提主动列出 | 生成登录页时于第 8 区块询问「是否需要账号体系」 |

#### 保守层（红线）

| 编号 | 规则 |
|---|---|
| R-13 | **意图保全校验**：增强结果必须包含原输入中的所有名词性实体（页面、功能、对象），缺失则视为失败 |
| R-14 | **禁止发明**：不得新增用户未提及的核心业务功能（可以补全表现形式，不能补全业务） |
| R-15 | **禁止删除**：用户明确说出的任何功能点都不得在增强结果中消失 |

> **R-13 的工程意义**：这是增强功能的「安全阀」。每次增强后自动执行实体比对，若发现原输入中的关键词在结果中缺失，则回退到未经增强的原始输入并提示用户，避免「增强反而丢需求」。

### 5.3 术语映射表（本地启发式使用）

| 正则 | 替换为 | 说明 |
|---|---|---|
| `好看｜美观｜漂亮` | 视觉层级清晰、留白充足、配色协调 | R-5 |
| `简洁｜简单点｜干净` | 信息密度低、弱化装饰、以内容为主体 | R-5 |
| `高级感｜质感` | 克制的色彩、精细的间距节奏、恰当的阴影层次 | R-5 |
| `不要太花｜别太花哨` | 降低色彩数量、避免渐变与装饰性图形 | R-5 |
| `现代｜时尚` | 扁平化、圆角适中、清晰的字阶 | R-5 |
| `扁平` | 无多余投影、以色彩与留白区分层级 | R-5 |

映射表可扩展，新增条目只需新增一行正则-替换对，无需改动增强逻辑。

## 6. 结果展示与使用

### 6.1 展示形态

增强结果以**卡片**形式出现在 AI 面板输入框上方：

```
┌──────────────────────────────────────────────┐
│ ✨ 已增强的提示词                    [还原]   │
├──────────────────────────────────────────────┤
│ ## 1. 产品概述                                │
│ 一个包含 3 个页面的移动端记账产品…            │
│ …（可滚动，最多 180px 高）                    │
├──────────────────────────────────────────────┤
│ ⚠ 已做的推断与补全：[推断] 未指定设备，按移…  │
├──────────────────────────────────────────────┤
│ [✓ 使用增强版生成] [复制] [重新生成]          │
└──────────────────────────────────────────────┘
```

### 6.2 三项操作

| 操作 | 行为 |
|---|---|
| **使用增强版生成** | 切换生成时使用的输入源。按钮呈选中态表示启用。未启用时用原始描述生成。 |
| **复制** | 把增强文本写入系统剪贴板，用户可粘贴到外部工具或手工微调 |
| **重新生成** | 重新执行一次增强（模型有随机性，可得到不同版本） |

### 6.3 可编辑性

- 增强结果**只读展示**，但**可通过复制到输入框再编辑**的方式实现修改
- 「还原」按钮清空增强结果，回到原始输入状态
- 是否使用增强版由**用户显式切换**，默认在增强成功后自动置为「使用增强版」（用户最可能的意图），但一眼可见、可一键切回

### 6.4 与生成流程的衔接

```
用户输入 → [增强提示词] → 展示增强卡片 → [使用增强版生成]
                                              ↓
                          生成引擎接收增强后的结构化文本
                                              ↓
                      阶段A 直接读取「页面结构」→ 无需再自行规划
                      阶段B 直接读取「视觉风格」→ Token 定稿有明确依据
                      阶段C 直接读取「关键区块」→ 逐页生成有骨架
```

增强后的文本天然契合生成流水线，**跳过了模型对模糊需求的猜测环节**，这是生成稳定性提升的主要来源。

## 7. 跨场景通用性与一致性

### 7.1 通用性保障

| 维度 | 保障机制 |
|---|---|
| **结构一致** | 固定 8 区块模板，任何输入输出骨架相同 |
| **术语一致** | 术语映射表全局唯一，相同口语表达在任何场景下被改写为相同术语 |
| **分级一致** | L0~L3 判定规则与场景无关，仅依赖输入本身特征 |
| **风格一致** | 未指定风格时统一回落到「清透蓝」，不随场景漂移 |

### 7.2 已覆盖场景类型

移动端 App / 微信小程序 / 平板应用 / 桌面端后台 / 企业官网 / 数据看板 / 电商场景 / 内容社区 / 工具类应用。

测试要点：同一功能点在移动端与桌面端描述下，增强结果应在**结构上同构**（同样的 8 区块），仅在设备与布局建议上不同。

## 8. 意图保全校验（工程实现）

```ts
// 伪代码
function verifyIntent(raw: string, enhanced: string): boolean {
  const entities = extractEntities(raw)      // 从原始输入抽名词性实体
  const missing = entities.filter(e => !enhanced.includes(e))
  if (missing.length > 0) {
    // 记录日志，回退到原始输入
    return false
  }
  return true
}
```

- **实体抽取**：优先采用「页面关键词 + 业务名词」的混合抽取
- **比对策略**：允许同义替换（通过术语映射表的反向表归一化后再比对）
- **失败处理**：回退到原始输入 + 提示「增强可能丢失了部分需求，已回退」

---

## 9. 幂等性

对**已经是增强格式的输出**再次执行增强，结果应基本稳定（不产生嵌套的元描述）。

保障手段：
- 输入分级时，含 8 区块特征（`## 1. 产品概述` 等）的输入直接判定为 L3
- L3 输入触发增强时，走「轻量规范化」分支：仅规范术语，不重建结构

---

## 10. 可测试性

增强器的**大部分逻辑是纯本地纯函数**，可脱离模型做单元测试：

| 测试项 | 输入 | 期望 |
|---|---|---|
| 分级判定 | `"记账"` | L0 |
| 分级判定 | `"帮我做个记账的 App，要有首页和报表"` | L1 |
| 分级判定 | 完整 100 字需求 + 风格 + 设备 | L3 |
| 术语规范化 | 包含「好看点」 | 输出含「视觉层级清晰」 |
| 设备推断 | `"做个网页后台"` | 输出含「桌面端」 |
| 页面抽取 | `"包含首页、详情页、购物车"` | 输出 3 个页面 |
| 意图保全 | 原输入含「优惠券」 | 增强结果仍含「优惠券」 |
| 幂等性 | 对增强结果再增强 | 结构不嵌套，长度增幅 < 20% |

实现位置：`src/services/ai/enhancer.ts`
纯函数导出：`classifyPrompt(raw)` / `enhanceHeuristic(raw)` / `verifyIntent(raw, enhanced)`

## 11. 与生成引擎的接口契约

```ts
// 增强（LLM 优先，失败回退本地）
enhancePrompt(raw: string, cfg?: ConfigPublic): Promise<EnhanceResult>

interface EnhanceResult {
  level: PromptLevel          // L0 | L1 | L2 | L3
  enhanced: string            // 8 区块 Markdown
  notes: string[]             // 已做的推断与补全，展示给用户
  usedLLM: boolean            // 是否由模型生成
}
```
