# 望舒 · 版本号规范

> 归属：望舒 · 工程规范
> 版本：v1.1 ｜ 状态：**生效中**
> 适用对象：产品版本、项目文件格式版本、Design JSON Schema 版本、文档版本
> 关联：`app/shared/version.ts`、`app/package.json`、`app/shared/design.ts`、`app/index.html`

---

## 1. 为什么需要单独一份规范

望舒里同时存在**四种**"版本"，它们变更的节奏完全不同。历史上它们被混着叫"版本号"，
导致过一次真实的事故：`electron/main/ipc.ts` 把产品版本写死成 `'1.0.0'`，
后来 `package.json` 升到新版本，而「关于」页与 MCP `initialize` 应答仍报 `1.0.0` ——
用户看到的版本和安装包对不上。

所以规则必须先分清"哪个版本"，再谈"怎么改"。

| # | 版本 | 含义 | 存放位置（唯一事实来源） | 变更触发条件 |
|---|---|---|---|---|
| 1 | **产品版本** `1.1.0` | 软件自身的发布版本 | `app/shared/version.ts` 的 `APP_VERSION` | 每次对外交付 |
| 2 | **项目文件格式版本** `1.0` | `.dsproj` 外层信封格式 | `app/shared/design.ts` 的 `FILE_VERSION` | 信封结构断裂（如 `design` 字段改名） |
| 3 | **Design JSON Schema 版本** `1.2` | 设计数据模型的形态 | `app/shared/design.ts` 的 `SCHEMA_VERSION` | 增删字段、改字段语义 |
| 4 | **文档版本** `v1.1` | 文档自身的修订号 | 各 doc 头部 `> 版本：` | 文档内容发生实质修订 |

**关键约束**：四者互不联动。产品版本升级**不要求**改 Schema 版本；
Schema 版本升级**必须**保证向后兼容（新增字段一律可选），否则产品版本必须升 MAJOR。

## 2. 产品版本规则（SemVer 2.0.0）

形如 `MAJOR.MINOR.PATCH`，三段都是非负整数，不带前缀 `v`（展示时才加 `v`）。

- **MAJOR**：不兼容的破坏性变更。
  例：项目文件格式断裂、IPC 通道语义反转、导出的 DESIGN.md 不再被旧版识别。
- **MINOR**：向后兼容的功能新增。
  例：新增 `pageGroups` 可选字段、新增 IPC 通道、新增 MCP 工具、新增界面能力。
- **PATCH**：向后兼容的缺陷修复。
  例：修掉窗口关不掉、修掉缩略图不刷新。

**升级判定口诀**：先问"旧版能不能读新版产出的文件？"
不能 → MAJOR；能但新增了能力 → MINOR；只是修错 → PATCH。

### 当前记录

| 产品版本 | 类型 | 主要内容 |
|---|---|---|
| `1.0.0` | 首发 | 核心四链路（生成 / 编辑 / 跳转 / 导出）+ 变体 + 提示词增强 + 四套主题 |
| `1.1.0` | MINOR | 项目管理（F-PM-01~09）：项目中心、界面数量 N 三档语义、DESIGN.md 互操作、方案分支、画布增强、本地 MCP 服务；SCHEMA `1.1 → 1.2`（全部新增字段可选，向后兼容） |

## 3. 唯一事实来源与同步清单

产品版本的**唯一**可写位置是 `app/shared/version.ts`：

```ts
export const APP_VERSION = '1.1.0'
```

其余位置**一律引用**，不得硬编码。需人工同步的只有 `package.json`（npm 与
electron-builder 不读 TS）：

```json
{ "version": "1.1.0" }
```

### 必须同步的位置（升级产品版本时逐项核对）

| 位置 | 方式 | 本次状态（1.0.0 → 1.1.0） |
|---|---|---|
| `app/shared/version.ts` | `APP_VERSION` 常量 | ✅ `1.1.0` |
| `app/package.json` | `version` 字段 | ✅ `1.1.0` |
| `app/package-lock.json` | 根 `version` 与 `packages[""].version` | ✅ 随 `npm install` 自动同步 |
| 窗口标题 / 「关于」区 | 引用 `APP_VERSION` | ✅ `AppSettingsPanel`、`HelpModal`、`ProjectHub` |
| MCP `initialize` 应答 | 引用 `APP_VERSION` | ✅ `electron/main/mcp-server.ts` |
| `app:info` IPC | 引用 `APP_VERSION` | ✅ `electron/main/ipc.ts` |
| 打包产物名 | electron-builder 模板 `${productName}-${version}-portable.${ext}` | ✅ `望舒-1.1.0-portable.exe` |
| 文档中的产品版本 | 人工 | ✅ 见 §4 清单 |

### 自动化护栏

`npm run test:project` 会断言下列事实，任一不成立即失败：

1. `VERSION_PATTERN.test(APP_VERSION)` —— 形态必须是三段式；
2. `package.json.version === APP_VERSION` —— 两条链不能分叉；
3. 版本比较函数 `compareVersion` 在典型用例上单调正确；
4. `docs/` 下所有形如 `望舒 v1.x`、`望舒[i]-1.x.y-portable.exe`、`望舒 Setup 1.x.y.exe`、`` `app/` @ v1.x.y `` 的产品版本标注都等于 `APP_VERSION`；
5. `scripts/test-*.mjs` 中**不存在** `schemaVersion === '字面量'` 形式的断言（应引用 `SCHEMA_VERSION`）；
6. `SCHEMA_VERSION` 与 `FILE_VERSION` 互不相等（证明两者独立）。

#### 历史记录的豁免

测试报告等文档会**忠实记录**当时的旧版本号 —— 那是史实，不该被改写。给这类行加行内标记即可豁免：

```markdown
| 打包产物重新生成 | `望舒-1.0.0-portable.exe`（该轮产品版本为 1.0.0） <!-- hist-version-ok --> |
```

豁免必须**逐行显式标注**，护栏会同时打印「扫描 N 处 / 豁免 M 行」，避免豁免被滥用成静默通道。

## 4. 文档版本标注约定

两类标注，含义不同，不要混用：

```markdown
> 版本：v1.1 ｜ 状态：**已实现**        ← 文档自身修订号（第 4 种版本）
> 产品：望舒 v1.1（纯本地桌面客户端）    ← 描述的产品版本，必须与 APP_VERSION 对齐
```

- 文章头部写 `> 产品：望舒 vX.Y` 的，随产品版本走，由护栏自动校验。
- 文章头部写 `> 代码基线：app/ @ vX.Y.Z` 的，随产品版本走。
- 文章头部写 `> 版本：vX.Y` 的，是**文档**修订号，文档实质改动时才 +1，护栏不校验。

## 5. 不随产品版本变动的版本

以下字面量**看似是版本号，但不是产品版本**，升级产品版本时**不要**改它们：

| 位置 | 值 | 说明 |
|---|---|---|
| `shared/design.ts` `FILE_VERSION` | `1.0` | `.dsproj` 信封格式，改它会让所有旧文件打不开 |
| `shared/design.ts` `SCHEMA_VERSION` | `1.2` | 设计数据模型形态 |
| `src/services/design/specs.ts` `SPEC_FILE_VERSION` | `1.0` | 规范文件（`*.speckit.json` / DESIGN.md）的格式版本 |
| `FILE_VERSION: '1.0'` 字面量 | `'1.0'` | 构造 `ProjectFile` 时的信封版本，语义同第 1 行 |
| `mcp-server.ts` `MCP_PROTOCOL_VERSION` | `2025-06-18` | MCP 协议版本，由协议方规定 |
| `package.json` `build.appId` | `com.local.designassistant` | 应用标识，改它会被系统当成另一个应用 |

## 6. 升级操作步骤（Checklist）

1. 改 `app/shared/version.ts` 的 `APP_VERSION`；
2. 改 `app/package.json` 的 `version`（保持与上一步一致）；
3. 跑一次 `npm install --package-lock-only` 同步 lock 文件；
4. 更新 §4 列出的文档产品版本标注；
5. 若涉及 Schema 变更，同步改 `SCHEMA_VERSION` 并在 `shared/design.ts` 注释里写清差异；
6. `npm run typecheck && npm run test:all`（含 `test:project` 版本一致性断言）；
7. `npm run build && electron-builder --win`，核对产物名中的版本号；
8. 打开应用「设置 → 应用设置 → 关于」与「使用说明」，确认展示版本与产物一致。
