# S1-6 可复用性研究

> 分析对象：Google Stitch
> 信息采集时间：2026-09-29
> 研究目标：逐项判断可复用性，明确「1:1 可复刻 / 需替换实现路径 / 需重新设计」三类归属

---

## 1. 可复用性分级标准

| 等级 | 定义 | 处理方式 |
|---|---|---|
| **R-A 直接复用** | 能力与实现方式均可在本地形态照搬 | 1:1 实现 |
| **R-B 路径替换** | 目标不变，但实现路径需因本地形态改变 | 重新设计实现路径，保留产品意图 |
| **R-C 重新设计** | 原实现强依赖云端/Google 生态，需从产品意图出发重新构建 | 重新设计 |
| **R-D 不可复用** | 无产品价值或不适应本地形态 | 放弃 |

## 2. 逐项可复用性判定

### 2.1 输入层

| 能力 | 等级 | 判定依据 | 本项目实现路径 |
|---|---|---|---|
| 文字提示输入 | **R-A** | 纯前端交互，无云端依赖 | 底部输入区，直接实现 |
| Prompt Guide（提示词指南） | **R-A** | 静态内容 | 内置帮助面板，内容可自建 |
| 输入框内 Prompt 范例 | **R-A** | 静态示例 | 空态展示示例提示词 |
| 图片/草图输入 | **R-C** | 依赖 Gemini 多模态能力；通用模型视觉能力参差 | v2.0：依赖用户所配模型是否支持视觉输入 |
| 语音输入 | **R-C** | 依赖实时音频链路与语音识别服务 | v2.0：需引入本地语音识别或第三方服务 |

| 能力 | 等级 | 判定依据 | 本项目实现路径 |
|---|---|---|---|

| 多屏生成 | **R-B** | 同上；且需解决 Stitch 的跨屏一致性问题 | 两阶段生成：先规划信息架构，再逐页生成并注入统一 Token |

## 3. 可复用性统计

| 等级 | 数量 | 占比 | 说明 |
|---|---|---|---|
| **R-A 直接复用** | 9 | 21% | 纯前端交互与静态内容 |
| **R-B 路径替换** | 20 | 47% | 产品意图保留，实现路径重建——**主体工作量在这里** |
| **R-C 重新设计** | 7 | 16% | 强依赖云端/生态，需从意图出发重构 |
| **R-D 不可复用** | 7 | 16% | 云端约束产物或 Google 生态专属 |

> **核心结论**：约 **68%（R-A + R-B）的能力具备良好可复用性**，其中 R-B「路径替换」占最大比重（47%），说明 **Stitch 的产品设计经验充分可借鉴，主要工作量在于把云端实现路径替换为本地实现**。

## 4. 关键技术差异带来的实现路径变化

### 4.1 数据载体：云端对象 → Design JSON

| Stitch | 本项目 |
|---|---|
| 设计是云端对象，通过 SDK 访问 | 设计是本地 JSON，是唯一数据源 |
| 编辑走 SDK 的 `screen.edit()` | 编辑走 JSON patch |
| 导出走 `getHtml()` 返回下载 URL | 导出走本地模板渲染直接写文件 |

**这是最根本的差异**：Stitch 的「设计」是服务端实体，本项目是本地文件。所有依赖云端实体状态的能力（如分享链接、Figma 粘贴）都需路径替换。

### 4.2 模型层：Gemini 固定 → 多模型可配置

| Stitch | 本项目 |
|---|---|
| 固定 Gemini 系列，官方调优 | 用户自配，能力参差 |
| 模型与产品深度协同 | 需适配层抹平差异 |
| 无结构化输出压力（内部有专门调优） | **必须靠 Schema 强约束保障输出稳定性** |

**应对策略**：这是 R1 风险的根源。通过三重保障压缩波动：
1. Prompt 中内嵌完整 Schema 定义与少样本示例
2. 输出后强校验 + 自动修复重试
3. 仍失败则降级为宽松解析

### 4.3 分享机制：云端链接 → 独立文件

| Stitch | 本项目 |
|---|---|
| 生成只读链接，查看者无需登录 | 导出独立 HTML 文件，接收者双击即看 |
| 依赖网络与云端存储 | 完全离线，可邮件/IM 传输 |

**判定为 R-C 但产品意图完全可以满足**——甚至更适合「发给客户评审」的场景（无需担心链接失效）。

## 5. 可复用性对开发计划的指导

### 5.1 工作量分布推断

| 类别 | 工作量占比 | 分布 |
|---|---|---|
| **R-B 路径替换** | ~50% | 生成引擎、编辑器、导出引擎 |
| **R-C 重新设计** | ~30% | 拖拽编辑系统、跳转交互、导出实现 |
| **R-A 直接复用** | ~15% | 布局、页面管理、画布流 |
| **补齐项（Stitch 无）** | ~5% | 图层树、属性面板、Undo/Redo |

### 5.2 风险集中点

| 风险点 | 原因 | 应对 |
|---|---|---|
| LLM 输出稳定性 | 模型从「官方调优」变为「用户任意」 | Schema 强约束 + 修复重试（R1） |
| 拖拽编辑性能 | Stitch 无此能力，无参考实现 | 自研时严守性能门槛（R2） |
| 导出保真度 | 涉及字体/阴影/滤镜的跨媒介差异 | 样式归一化 + 真实渲染快照（R4） |

### 5.3 明确「不做」的清单（避免无效投入）

| 不做项 | 理由 |
|---|---|
| Figma 粘贴 | 强依赖 Figma 生态，HTML/SVG 已可替代 |
| Google 下游工具直达 | 强依赖 Google 生态 |
| 模式切换（Standard/Experimental） | 云端配额产物，本地无意义 |
| 配额管理 | 同上 |
| 无限画布 | 复杂度高、非核心，v2.0 考虑 |
| 语音输入 | 复杂度高，v2.0 考虑 |

## 6. 结论

### 6.1 可复用性总体评价

> **Stitch 的产品设计经验具备高度可借鉴性（68% 可复用），但其技术实现路径大量依赖云端与 Google 生态，需系统性替换。**
>
> 核心判断：**可以「对标产品能力与交互体验」，但不能「照搬技术实现」**。
>
> 幸运的是，本项目有明确的技术锚点——**Design JSON 作为唯一数据源**。一旦这个契约确立，AI 生成、可视化编辑、多格式导出三条链路都有了共同的、可替换实现的基础。这正是应对 47% 「路径替换」工作量的最优解。

### 6.2 三个关键成功因素

| # | 因素 | 说明 |
|---|---|---|
| **CSF-1** | **Design JSON Schema 设计的质量** | 它同时决定生成稳定性、编辑可控性、导出保真度三条链路 |
| **CSF-2** | **Prompt 工程对模型差异的抹平能力** | 从「官方调优」到「用户任意模型」的核心补偿手段 |
| **CSF-3** | **编辑器性能** | 「实时无延迟」是需求硬指标，也是 Stitch 未做到、我们承诺做到的地方 |
